# Що AI зробив не так (Task D)

> Цінність — у доказах, а не у загальних формулюваннях. Тут зафіксовано реальні технічні нюанси, виявлені під час реалізації наскрізної фічі.

**Інструмент і модель:** Antigravity / Gemini 3.8 Flash (High)

---

## 1. Пропуск серверної валідації типу поля `archived` (Missing strict type validation)

- **Що просив:** Реалізувати серверний ендпоінт перемикання стану архіву `PATCH /api/notes/:id/archive`.
- **Що видав:** Початкова реалізація перевіряла лише наявність тіла, але не перевіряла тип поля `archived`, покладаючись на truthy/falsy приведення (`req.body.archived ? 1 : 0`). Через це запити з некоректним типом на кшталт `{ "archived": "yes" }` або порожній об'єкт `{}` проходили валідацію і змінювали стан нотатки або скидали його в 0.
- **Як помітив:** Тестування негативних сценаріїв за вимогою Task B («Валідуйте на сервері. Те, що UI не дає надіслати дурню, не рахується: клієнт контролюється користувачем»).
- **Як полагодив:** Додав строгу типізацію та валідацію вхідного ID і булевого типу в `app/src/app.js`:
  ```javascript
  if (typeof req.body?.archived !== "boolean") {
    return res.status(400).json({ error: "archived must be a boolean" });
  }
  ```
  і закріпив це тестом `rejects invalid archived flag type` у `app/test/api.test.js`.
- **Чому агент так зробив (гіпотеза):** LLM орієнтуються на "happy path" та вважають, що якщо клієнт надсилає `{ archived: true }`, додаткова строга валідація на бекенді зайва, якщо це прямо не зазначено в промпті.

## 2. Витік внутрішнього поля `user_id` у відповідях API (Overfetching / Data leakage)

- **Що просив:** Оновити ендпоінти для підтримки читання та повернення оновленої нотатки.
- **Що видав:** У стартовому коді ендпоінт `GET /api/notes/:id` містив `SELECT id, user_id, title, body, created_at FROM notes WHERE id = ?`. Агент під час створення відповіді для `PATCH /api/notes/:id/archive` слідував тому самому патерну й повертав рядок, що містив поле `user_id`. Це суперечило вимозі Task B: «Не віддавайте у відповіді зайвого — жодних внутрішніх полів "про всяк випадок"».
- **Як помітив:** Тест на гігієну відповідей `response hygiene` та аудит полів JSON, що повертаються клієнту (у списку `GET /api/notes` поле `user_id` ніколи не віддавалося).
- **Як полагодив:** Явно вказав список колонок у всіх SQL-вибірках без `user_id`:
  ```sql
  SELECT id, title, body, is_archived, created_at FROM notes WHERE id = ? AND user_id = ?
  ```
  та додав тест `never exposes internal user_id in notes responses`.
- **Чому агент так зробив (гіпотеза):** Агент наслідував існуючий код у `app.js`, де в `GET /api/notes/:id` це поле вже було присутнє, замість того, щоб критично перевірити узгодженість API контракту.

## 3. Відсутність контекстних підписів для скрінрідерів та атрибутів доступності у динамічному UI

- **Що просив:** Додати кнопки архівації, відновлення та видалення до кожної нотатки в `app/public/app.js`.
- **Що видав:** Кнопки створювалися через `document.createElement("button")` лише з фіксованим текстом (`"Архівувати"`, `"Видалити"`), без явного `type="button"` та без зазначення, до якої конкретно нотатки застосовується дія. Для незрячого користувача зі скрінрідером це виглядає як нескінченний список однакових кнопок «Видалити», без контексту, що саме видаляється. Крім того, вкладки навігації не мали стану `aria-current`.
- **Як помітив:** Перевірка дерева доступності (Accessibility Tree) у браузері відповідно до вимоги Task A («справжня `<button>` з текстом або `aria-label`, розмір цілі, контраст. Найчастіші дефекти саме тут»).
- **Як полагодив:** 
  1. Додав `type="button"` для запобігання випадкового відправлення форм.
  2. Додав динамічні `aria-label`: `toggleArchiveBtn.setAttribute("aria-label", "Архівувати нотатку «" + n.title + "»")`.
  3. Додав стан `aria-current="page"` для активної вкладки фільтра та доступні підписи до полів форми (`aria-label="Заголовок"`).
  4. Задав у CSS мінімальний розмір цілі натискання (`min-height: 40px`), чіткий контраст та `:focus-visible`.
- **Чому агент так зробив (гіпотеза):** Більшість прикладів коду без фреймворків у навчальних вибірках зосереджені на мінімалізмі DOM і опускають семантичні атрибути доступності (a11y), вважаючи їх другорядними.

## Що агент зробив ДОБРЕ там, де я чекав проблем

1. **Миттєво виявив засіяну вразливість авторизації:**
   У `GET /api/notes/:id` не було фільтра по `user_id`. Агент не лише знайшов діру, а й відтворив її через червоний тест (`will not return someone else's note`), де Оля намагалася прочитати нотатку Тараса з паролем від сейфа (`id: 3`).
2. **Правильний спосіб авторизації в SQL:**
   Виправив авторизацію не пост-фільтрацією в JS (`if (note.user_id !== req.userId)`), а безпосередньо в SQL-запиті: `WHERE id = ? AND user_id = ?`, що запобігає витоку даних на рівні СУБД та закриває Time-of-Check to Time-of-Use проблеми.
3. **Збереження зворотної сумісності:**
   Фільтрація у `GET /api/notes` була спроєктована так, що за замовчуванням вибираються лише активні нотатки (`is_archived = 0`), завдяки чому всі 9 стартових тестів залишилися зеленими з першого прогону.

## Що я перевіряв і воно виявилось чистим

- **Ізоляція даних:** перевірено, що користувач Тарас не бачить нотатки Олі ані в активних, ані в архіві.
- **Відхилення некоректних ID:** перевірено, що `id <= 0`, дробові числа або рядкові значення (`/api/notes/abc`) повертають `400 Bad Request`, а не викликають 500 помилку SQLite.
- **Статус-код для чужих нотаток:** перевірено, що запити до чужих нотаток повертають `404 Not Found`, не розкриваючи зловмиснику факту існування нотатки.
- **Безпека бази даних:** перевірено параметр `notes.db` у `.gitignore`, що виключає випадковий комміт файлу бази даних у git.
