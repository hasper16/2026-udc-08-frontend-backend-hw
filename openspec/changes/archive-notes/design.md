# Technical Design: Note Archiving

## Context

Застосунок побудовано на базі Node.js, Express, SQLite (`better-sqlite3`) та ванільного браузерного JavaScript без збірки. Автентифікація реалізована як псевдосесія через заголовок `x-user-id`. Детальніше щодо мотивації див. у `proposal.md`.

## Goals / Non-Goals

**Goals:**
- Забезпечити наскрізну архівацію та відновлення нотаток без додавання бандлерів чи зовнішніх бібліотек.
- Виправити діру в авторизації `GET /api/notes/:id`, гарантуючи, що жоден користувач не може переглянути чужий вміст.
- Забезпечити бездоганну доступність (WCAG / a11y) у браузері.

**Non-Goals:**
- Справжня автентифікація (JWT/куки) — поза скоупом воркшопу.
- Зміна структури сесій чи додавання складних ролей користувачів.

## Decisions

### Рішення 1: Булевий прапорець у SQLite замість мітки часу
- **Обрано:** `is_archived INTEGER NOT NULL DEFAULT 0`.
- **Альтернативи:** `archived_at TEXT` (timestamp).
- **Чому:** Простіше для фільтрації, не створює часових колізій та надійно підтримується простим індексом або запитом.

### Рішення 2: `PATCH /api/notes/:id/archive` із булевим прапорцем
- **Обрано:** `PATCH /api/notes/:id/archive` із тілом `{"archived": true | false}`.
- **Альтернативи:** `POST /api/notes/:id/archive` та `POST /api/notes/:id/unarchive`.
- **Чому:** Ідемпотентний REST-підхід із явною серверною валідацією типу `typeof req.body?.archived === "boolean"`.

### Рішення 3: Повернення `404 Not Found` для чужих нотаток
- **Обрано:** `404 Not Found` замість `403 Forbidden`.
- **Альтернативи:** `403 Forbidden`.
- **Чому:** Запобігає перебору ID (enumeration attacks), не розкриваючи зловмиснику наявність запису у базі. Узгоджено з наявною реалізацією `DELETE /api/notes/:id`.

### Рішення 4: Перевірка прав безпосередньо в SQL
- **Обрано:** `WHERE id = ? AND user_id = ?`.
- **Альтернативи:** Отримання запису та перевірка в пам'яті Node.js (`if (note.user_id !== req.userId)`).
- **Чому:** Усуває можливість витоку даних на рівні пам'яті процесу та є найбільш продуктивним і безпечним патерном.

## Risks / Trade-offs

- **[Ризик] Помилки вводу при прямому зверненні до API без UI:**
  → *Мітигація:* Серверна валідація на типи та валідність числових ID перед виконанням SQL-запитів.
- **[Ризик] Доступність динамічних елементів у ванільному DOM:**
  → *Мітигація:* Використання семантичних тегів `<button type="button">`, обов'язкових `aria-label` для екранних читачів та `aria-current="page"` на вкладках.
